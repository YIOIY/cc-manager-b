# 用户之声设计（2026-11-13）

## 为什么做

用户要一个「用户之声」板块，收集大家在使用过程中遇到的问题。现在的情况是：操作员遇到报错或看不懂的地方只能私下找管理员（这两天的 403、复制失败、「修改」变新建都是这样冒出来的），问题没有记录，也不知道处理到哪一步。

## 目标 / 非目标 / 反目标

- 目标：任何登录用户在任何页面都能随手提一条反馈，自动带上所在页面和出错信息；自己能看到处理状态和回复；管理员在一个地方看到全部、筛选、回复、改状态。
- 非目标：不做消息通知（邮件、站内信）、不做多轮评论、不做附件和截图上传、不做对外的公开反馈页。
- 反目标：反馈里自动夹带密码、令牌、搜索词等敏感内容；普通用户能看到别人的反馈；提交反馈比在聊天里说一句还麻烦。

## 方案比较

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A 站内反馈 + 处理状态（采用） | 一张表、四个接口、一个提交弹窗、一个列表页 | 记录留在系统里，能跟上下文（页面、错误码、请求编号）和审计对上；需要一点开发 |
| B 只放一个外部链接 | 跳到表单工具或聊天群 | 不用开发，但上下文靠用户自己描述，状态无从跟踪，数据在别处 |
| C 复用审计日志 | 把反馈写成审计事件 | 审计是只追加的操作记录，没有状态和回复，查看需要审计权限 |

## 设计

**数据**：迁移 v13 新表 `feedback(id, user_id, username, kind, title, body, page, context_json, app_version, status, reply, handled_by, handled_at, version, created_at, updated_at)`。

- `kind`：`problem`（遇到问题）、`suggestion`（功能建议）、`other`。
- `status`：`open`（待处理）→ `in_progress`（处理中）→ `resolved`（已解决）/ `closed`（不处理）。
- `context_json` 只接受白名单键：`error_code`、`request_id`、`user_agent`、`viewport`，每个值限长；`page` 只存路径（不含查询参数，避免带上搜索词）；`app_version` 由服务端填。

**接口**（均需登录）：

| 接口 | 说明 |
| --- | --- |
| `POST /feedback` | `{kind, title?, body, page?, context?}`；`body` 必填、最多 2000 字，`title` 最多 80 字（留空取正文开头）。201 `{id}`。审计 `feedback.create`。受现有写限速保护。 |
| `GET /feedback` | 分页列表，可按 `status`、`kind`、`q` 筛选。有 `feedback.manage` 的人看到全部，其他人只看到自己的。返回 `items`、`total`、`counts`（各状态数量，范围同列表）、`can_manage`。 |
| `PATCH /feedback/{id}` | 需 `feedback.manage`：`{status?, reply?, expected_version}`；`reply` 最多 1000 字。版本不符 409。审计 `feedback.update`。 |
| `GET /feedback/summary` | `{open}`：有 `feedback.manage` 时是全部待处理数，否则是自己待处理的数量。用于导航上的数字。 |

**权限**：权限目录新增模块「用户之声」和一项 `feedback.manage`（处理用户反馈）。管理员自动拥有；提交和查看自己的反馈不需要权限。README 权限数 33 → 34。

**前端**：

- 顶栏右侧常驻「反馈」按钮，任何页面可点；弹窗里选类型、写描述（标题可不填），下方说明会附带哪些信息（当前页面、浏览器；从报错处进入时还有错误码和请求编号）。提交后提示已收到，并可跳到「用户之声」。
- 报错提示（`ErrorNotice`）里加「反馈这个问题」，点了直接打开弹窗并带上错误码和请求编号。
- 侧边栏新增「用户之声」页面（不需权限）：顶部按状态筛选并显示数量；每条显示类型、标题、正文、提交人与时间、所在页面、状态、回复。管理员每条有「处理」：改状态、写回复。有待处理时导航项显示数字（仅管理员）。
- 帮助文档加一篇「反馈问题和建议」。
