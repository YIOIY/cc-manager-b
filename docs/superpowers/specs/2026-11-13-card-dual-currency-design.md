# 账号卡片：人民币 + 美元金额与汇率（2026-11-13）

## 为什么做

账号卡片的「累计花费」只有人民币（平台 `cpa_usage.cost`，单位百万分之一元）。用户要同时看到美元金额和所用汇率，方便和 Claude 的美元定价对照；并去掉卡片底部一直为空的「请求 / 输入 / 输出」三行（它们来自从未开通的 OpenAPI 指标）。

## 目标 / 非目标 / 反目标

- 目标：卡片「累计花费」同时显示人民币、换算出的美元、汇率及其日期；汇率自动更新，无需人工维护；删除三行进度条。
- 非目标：不改仪表盘、账单页的金额展示；不做手动设置汇率；不保存历史汇率曲线。
- 反目标：汇率取不到时显示一个错误或过期很久却不标明的美元数字；因为汇率接口慢或不可用而拖慢、阻塞账号列表；把任何账号数据发给汇率接口。

## 方案比较

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A 自动取公开参考汇率（采用） | 服务端每 6 小时请求公开汇率接口，存库；前端读取后换算 | 无需维护；多一个对外只读请求；与供应商内部结算汇率可能有出入，所以美元标「≈」并显示所用汇率 |
| B 管理员手填固定汇率 | 平台设置里加一个汇率输入框 | 可与供应商口径对齐，但要人记得更新；多一处设置和权限 |
| C 环境变量配置 | 每台服务器写死一个值 | 最简单，但两台服务器都要登录修改，页面上无法知道何时更新过 |

选 A。若以后需要与供应商口径对齐，可在 A 之上加"手动覆盖"。

## 设计

- **来源**：依次尝试 `https://api.frankfurter.dev/v1/latest?base=USD&symbols=CNY`（欧洲央行参考汇率）和 `https://open.er-api.com/v6/latest/USD`；两者都返回 `rates.CNY`。只发送 GET，不带任何业务数据；单次超时 15 秒，响应限 64 KiB；汇率须在 1–20 之间才接受。2026-11-13 已确认两台服务器及容器内均可访问。
- **存储**：迁移 v11 新表 `exchange_rates(pair PRIMARY KEY, rate, source, rate_date, fetched_at)`，只保留最新一条 `USD/CNY`。取数失败不覆盖已有汇率。
- **更新**：后台任务启动 15 秒后取一次，之后每 6 小时一次。
- **接口**：`GET /api/v1/exchange-rate`（登录即可）→ `{pair: "USD/CNY", rate, source, rate_date, fetched_at}`；还没有汇率时 `rate` 为 `null`。
- **前端**：`useExchangeRate()` 全页面共享一份汇率（首次使用时加载，失败静默）；`fenToUsdCents(fen, rate)` 四舍五入到美分。`PlatformUsageBlock` 的「累计花费」占满一行：
  ```
  累计花费
  ¥751.04   ≈ $112.63
  汇率 1 美元 = 6.6683 人民币 · 2026-11-12
  ```
  没有汇率时只显示人民币并注明「汇率暂不可用」；汇率超过 3 天未更新时在日期后标「可能过期」。
- **卡片**：删除「请求 / 输入 / 输出」三行及其只为它们服务的计算；OpenAPI 指标块（有数据才显示）保留。
- **帮助文档**：常见问题加一条「卡片上的美元金额是怎么算的」。
