# 供应商账单查询与同步补齐方案

日期：2026-11-05。状态：核心方案已实施并完成本地模拟验收；本文保留设计依据，实际接口、差异与验证见 [实施记录](bill-query-implementation-report.md)。真实供应商尚未联调。

本方案依据本次读取的供应商登录页面 OpenAPI 文档、当前 Go/Vue 源码和本地复现结果编写。供应商字段说明与本地产品规则分开描述；真实供应商查询仍未联调。

## 1. 范围与完成目标

本轮完成 `/supplier-account/api/openapi/bill/query` 的请求、解析、持久化、历史补采、查询和反馈闭环。`/supplier-account/api/openapi/metrics/query-keys` 继续不接入，不新增 API Key 输入、查询或存储能力。

完成后的用户路径：选择平台连接、账号和日期 → 查询已保存账单与区间合计 → 查看缺失或过期情况 → 主动补采指定范围 → 查看真实进度、失败项与结果 → 刷新同一条件的账单。

范围内保留已有登录、CSRF 和加密方式；这轮不扩展系统计费、收益结算、账号上传或 OAuth 生命周期。现有 metrics 查询保留；账单调度与 metrics 调度解耦。

| 问题 | 当前行为 | 修改后的行为 |
| --- | --- | --- |
| 日期范围 | 客户端支持，业务固定最近三天 | 用户可查询本地历史并主动补采上游允许的日期 |
| 账号选择 | 只对已有关联逐个发送 | 本地账号选择，经后端映射后按连接、日期、最多 100 个账号分批 |
| 返回窗口 | 丢弃 `range` | 解析、规范化、校验并保存实际窗口 |
| 查询完整性 | 截取 1000 条后前端筛选 | 服务端筛选、分页、总数与全结果合计 |
| 同步反馈 | 失败可能提示完成 | 持久任务，区分排队、进行、成功、部分失败、失败、被中断 |
| 账号 ID | 把上游 `id` 标为平台 ID | 本地账号 ID、供应商账号 ID、平台账号 ID 分开 |
| 90 天限制 | 使用连续小时比较 | 使用平台连接时区中的业务日期比较 |
| 历史错误零值 | 无验证标记 | 保留原值并标为待复核，成功重查后更新 |

## 2. 上游契约与本地规则

### 2.1 已读取的上游契约

路径：`POST /supplier-account/api/openapi/bill/query`，使用后端保存的 OpenAPI Bearer Token。

| 参数 | 类型 | 上游说明 | 本地映射 |
| --- | --- | --- | --- |
| `account_ids` | number[] | 单次最多 100 个；上号返回的 `id` | 从 `platform_links.upstream_id` 获取，转为正整数后发送 |
| `start_ds` | string | `YYYYMMDD` 或 `YYYY-MM-DD`；不得早于 90 天前 | 统一生成 `YYYY-MM-DD` |
| `end_ds` | string | 同上，不早于开始日期 | 日采集时与 `start_ds` 相同 |

响应 `list[]` 包含 `id`、`request_count`、`prompt_tokens`、`completion_tokens`、`cache_read_input_tokens`、`cache_write_input_tokens`、`cost`；`range.start_ds/end_ds` 回传实际生效窗口，文档示例为 `YYYYMMDD` 整数。`cost` 为人民币元，本地转为整数分。

接口返回区间汇总，无法从一次多日查询得到真实逐日明细。因此补采采用逐日查询，多账号同日合并。页面区间合计从已保存日账单求和。

### 2.2 明确为本地产品规则的部分

- 同步结束日期不晚于连接时区的今天；此限制是本地规则，不声称供应商已明确禁止未来日期。
- 日期边界使用有效的连接 IANA 时区；配置缺失或无效时阻止主动同步并返回配置错误，不回退到执行机器时区。
- 读取本地历史不受上游 90 天限制；超出窗口的数据可以展示，但无法重新采集。
- 自动同步默认排除已归档账号，历史查询仍可查看其账单；手动补采可显式勾选归档账号。
- 一次查询或同步只属于一个连接，避免不同平台、账号 ID 命名空间和业务时区混算。
- 上游约 2 小时的延迟作为提示，不作为完整性或最终结算保证。

### 2.3 90 天日期边界

取连接时区中的日期 `today`，下界为 `today.AddDate(0, 0, -90)`；校验 `lower <= start <= end <= today`。用日历日期比较，禁止 `time.Since(start) > 90*24*time.Hour`。

例如，以 2026-11-05 为业务日，下界是 2026-08-07；中午和晚上应得出相同结果。包含下界和今天时有 91 个日期，不把“开始日期不早于 90 天前”误写成“最多 90 个日期”。默认“最近 90 天”快捷项可选择今天及之前 89 天，与可查下界分别定义。

这是根据文档日期语义采用的本地实现口径；真实平台是否在边界额外限流或裁剪，需通过最终受控联调确认。上游如返回不同实际窗口，按第 3 节处理。

## 3. 供应商客户端修改

修改 `internal/supplier/client.go`，保留已经修复的账单 JSON tag 和精确金额解析。

### 3.1 使用完整响应类型

建议新增 `BillQuery`、`BillQueryResult`、`BillDateRange`：

```go
type BillQuery struct {
    AccountIDs []int64
    StartDate  string // 规范化的 YYYY-MM-DD
    EndDate    string
}

type BillDateRange struct {
    StartDate string
    EndDate   string
}

type BillQueryResult struct {
    Bills          []Bill
    RequestedRange BillDateRange
    ActualRange    BillDateRange
}
```

`QueryBills(ctx, query)` 返回 `BillQueryResult`。同步服务负责根据连接时区和可注入时钟校验业务日期；传输层校验格式、顺序和 1～100 个 ID，不再独立使用机器本地时间判断 90 天限制。

变更返回类型时，同时更新 `onboard.go`、账单 worker、已有 `syncBillsForLink` 和测试，防止某条写入路径绕过完整响应校验。

### 3.2 校验响应再写入

1. 兼容 `range` 日期为文档中的八位数字，以及八位/带横线字符串，统一规范化；缺失或无效时返回 `BILL_RANGE_INVALID`。
2. 对每个逐日请求，实际起止必须与请求日一致。出现裁剪或扩大时返回 `BILL_RANGE_MISMATCH`，记录脱敏的请求/实际日期，保留旧账单，不把多日总额存为某一天。
3. 按返回 `id` 匹配请求账号，拒绝重复 ID、未请求 ID 和无效 ID；不再依赖 `bills[0]` 的位置。
4. 计数必须为非负整数，存在且可解析；金额使用精确十进制，拒绝溢出和超过分精度的非零小数。对 null/字段缺失不默认填 0。
5. 同批结构和窗口错误阻止整批入库；窗口正确时，单行数值异常只使对应账号日失败，其余有效账号可更新。
6. 有效且显式为 0 的值正常保存为 0。账号未出现在 `list` 中记为 `no_data`，不制造零账单，不删除旧值。

上游没有确认“未返回账号一定是零用量”，所以 `no_data` 与“成功返回零值”必须分开。

## 4. 本地 API 修改

新增专用接口，保留现有 GET 数组响应以兼容当前调用方。新增接口均沿用已有 `{data: ...}`、`{error: ...}` 封装和登录/CSRF 规则。以下 JSON 为拟定契约。

### 4.1 查询本地日账单

`POST /api/v1/platform-usage/bills/query`，只读本地，不隐式访问上游。

```json
{
  "connection_id": "connection-local-id",
  "account_ids": ["account-local-id"],
  "from": "2026-10-07",
  "to": "2026-11-05",
  "q": "账号、别名或 ID",
  "include_archived": false,
  "revision_min": null,
  "page": 1,
  "page_size": 20,
  "sort": "bill_date_desc"
}
```

- `connection_id` 必填；`account_ids` 是本地 ID，省略表示该连接中符合条件的全部账号。
- 起止日期必填，支持本地已保存的更早历史；前端默认最近 30 天。`page_size` 只允许 10、20、50、100。
- 关键词、归档、修订次数、账号、日期全部在 SQL 层生效；排序字段采用白名单，默认按日期、账号 ID、行 ID 稳定排序。
- 一次数据库读事务内生成当前页、总数、全匹配范围的合计和覆盖摘要，避免页面与合计来自不同快照。
- 响应结构为 `items`、`pagination`、`totals`、`coverage`、`timezone`；`total` 不再是截取的 1000 条数量。
- 每行明确返回 `account_id`、`connection_id`、`supplier_account_id`、可选 `platform_account_id`、账号名称、账单日期、各类计数、金额、更新时间、revision、验证与采集状态。
- ID、各类计数和 `cost_fen` 对浏览器使用十进制字符串，避免超过 JavaScript 安全整数后精度丢失；页数、页大小、常规任务数量可以使用 number。新页面使用专用格式化函数。

`totals` 汇总所有匹配行，不受分页影响。摘要说明“已保存数据合计”；存在未复核、缺失、无返回、过期或失败项时同时返回 `is_partial: true`，不得标注为完整期间消费。

`coverage` 以“账号 × 业务日”为单位返回期望项数、已验证有值项、历史未复核项、未同步项、最近无返回项、最近失败项及最新采集时间。只有期望集合全部具有有效值时 `complete=true`。已归档或已解除关联但仍有历史的账号保留其行，明确不能通过现有连接补采；不要因为关联消失而从合计中静默删除历史记录。

查询中的 `q` 和 `revision_min` 用于过滤已保存行；它们不能证明某账号日“不应存在”。覆盖摘要按选定连接、账号和日期计算，字段返回 `coverage.scope="account_date_selection"`，页面与行筛选结果分别标注。

### 4.2 主动补采账单

`POST /api/v1/platform-usage/bills/sync`，创建持久任务后立即返回 HTTP 202。

```json
{
  "connection_id": "connection-local-id",
  "scope": "selected",
  "account_ids": ["account-local-id"],
  "from": "2026-10-07",
  "to": "2026-11-05",
  "include_archived": false
}
```

- `scope=selected` 必须提供非空本地账号 ID；`scope=all_linked` 表示该连接全部可同步关联，禁止用空数组暗示“全部”。
- 验证连接已启用、时区有效、Token 可解密、所选账号确有该连接下的上游关联，并执行日期校验。
- 客户端不能直接替换 `supplier_account_id` 或填入其他连接的 ID。
- 默认只补齐明确选择的账号和日期；关键词与修订次数不会偷偷成为同步范围。前端展示“同步 N 个账号、起止日期”，与本地表格筛选区别明确。
- 接收 `Idempotency-Key`；同键同请求返回原任务，同键异请求返回 409。没有幂等键也按规范化参数复用同一活动任务；终态后的新主动同步允许创建新任务以吸收修订。
- 建议初始任务上限为 10000 个账号日，可配置。这是本地资源限制；超限返回 422 与实际计算数量，用户可缩小范围。
- 返回 `run_id`、`state=queued`、`total_items`、`planned_requests`、已解析的账号数、日期范围和 `reused`；有任务前置校验错误直接返回对应 4xx，不假装接收成功。

### 4.3 任务进度与失败项

- `GET /api/v1/platform-usage/sync-runs/{run_id}`：返回总体状态、进度、更新时间及计数。
- `GET /api/v1/platform-usage/sync-runs/{run_id}/items?state=failed&page=1&page_size=20`：分页查看失败、无返回或其他状态明细。
- `POST /api/v1/platform-usage/sync-runs/{run_id}/retry-failed`：只重试仍在可查窗口内的失败账号日，创建有父任务引用的新任务；新任务不重放账号上传。

进度数量统一为账号日，不混用账号数与 HTTP 请求数。建议返回 `total`、`completed`、`updated`、`unchanged`、`no_data`、`failed`、`superseded`，并单独返回 HTTP 请求与重试数量。

任务终态规则：有效项全部处理且无失败/被替代项为 `succeeded`；同时有可用结果和失败/被替代项为 `partial`；全部失败为 `failed`；全部被替代或进程中断且尚未恢复为 `interrupted`。`no_data` 表示查询成功但没有返回值，可计入已处理，不代表覆盖完整。

### 4.4 兼容已有接口

- 保留 `GET /platform-usage/bills` 和现有单账号详情返回结构，内部复用筛选与映射代码；旧 `platform_account_id` 字段暂时保留并标为废弃别名。
- 新增明确的 `supplier_account_id`，真正的 `platform_account_id` 从已有 `aid` 映射取值，无值返回 null。新页面只用新定义。
- 现有 `POST /platform-usage/sync` 作为兼容入口，改为调度指标与账单任务并返回任务引用；202 文案表示已排队，不再表示采集完成。
- 先部署新查询与任务接口，再让前端切换；旧前端停止提示假成功之后再改变兼容入口的执行方式。

## 5. 持久化与迁移

使用带版本号的事务迁移，不继续忽略 `ALTER TABLE` 的任意错误。迁移前保留 SQLite 一致性备份；对正在运行的库使用 SQLite backup API，不能只复制主库而遗漏 WAL。

### 5.1 日账单表

保留 `UNIQUE(account_id,connection_id,bill_date)`、现有计数和金额列。增补以下字段，名字在实施时与 SQL 命名统一：

| 字段 | 用途 |
| --- | --- |
| `requested_start_ds` / `requested_end_ds` | 请求日期 |
| `actual_start_ds` / `actual_end_ds` | 上游实际日期，旧记录允许 null |
| `source_timezone` | 本次采集连接时区快照，旧记录可为未知 |
| `response_verified` | 是否通过本轮完整窗口与字段校验 |
| `write_generation` | 新采集流程的单桶代次，从 0 开始 |
| `last_changed_at` | 数值最后发生变化的时间 |

保留 `source_range_json` 供兼容与诊断；新值写实际窗口。旧值只视为历史请求范围记录，不自动升级为供应商确认。

旧 `sync_generation` 当前存储纳秒时间戳，不把新的自增任务 ID 与其混用比较。账单并发控制统一切换至新 `write_generation`；metrics 表暂不变。

补充 `(connection_id,bill_date,account_id)` 等查询索引。`platform_links` 中的 ID 关联不通过改值来“修复命名”；问题在 API 和展示语义。

### 5.2 同步任务表

复用 `sync_runs`，新增账单专用 kind 及原始规范化选择、创建时间、总账号日数、完成分类计数、去重摘要、父任务 ID、更新时间和租约字段；保持老指标记录可读。

新增 `bill_sync_items`：

- 每行一个连接、账号、日期；唯一约束 `(run_id,connection_id,account_id,bill_date)`。
- 保存上游账号 ID 与时区快照、状态、attempts、next_attempt_at、generation、错误码、脱敏错误、开始和结束时间。
- 上游关联或连接配置在排队期间变化时，执行前验证；已改变的身份映射阻止该项执行，不能把旧账号结果写入新关联。

新增 `bill_sync_buckets`：以 `(connection_id,account_id,bill_date)` 为唯一键，保存当前已分配 generation 与最后尝试的状态、时间。记录 no_data 或失败而不覆盖历史数值；支持无账单行时的覆盖统计。

幂等记录复用现有机制时必须增加 namespace，避免与账号上传共用同一 key 空间；任务创建和幂等占用在同一个事务内完成。

### 5.3 修订、空值与历史错误值

- 同一账号日重查采用覆盖更新，禁止累加采样。
- 有效数值未变化时只更新采集时间和验证元信息；数值变化时 `revision + 1` 并更新 `last_changed_at`。旧版已经增加的 revision 保留，迁移后采用新语义。
- 空响应、字段异常或网络失败保留旧数值；页面显示最近尝试状态与旧值采集时间，不能将旧值呈现为本次新采集结果。
- 本地没有供应商“最终账单”字段依据，不根据经过几天就自动设置 `finalized=true`；页面显示可修订和采集时间。
- 全部既存行迁移为 `response_verified=false`，原因是旧版本既未验证返回窗口，也可能受到计数字段解析问题影响。不能凭数字为 0 就批量推断真实用量。
- 对允许窗口内的未复核行提供补采；窗口外保留原始金额和计数并标注历史未复核，不编造修正值、不清空数据。

## 6. Worker 与并发控制

### 6.1 分片

1. 将本地选择解析为连接内账号关联快照。
2. 在连接时区生成包含起止日的日期列表。
3. 每个业务日按最多 100 个上游 ID 分组；按 ID 回填每个账号日结果。
4. 例如 250 个账号查 3 天：9 次上游请求、750 个账号日；不再发送 750 次逐账号请求。
5. 只在收到并验证结果后写日账单；异常一律落到对应任务项，不被 `_ = ...` 丢弃。

### 6.2 执行顺序和代次

- 首版默认同一连接一次一个上游账单请求、全局最多两个；连接的最小请求间隔建议先设为 1 秒，可配置。数字是本地保守默认，不代表上游公布的配额。
- 调度器领取任务项时，在短事务中领取租约并为对应账号日分配单调递增 generation；网络请求在事务外执行。
- 返回后在同一写事务检查：任务租约仍有效、关联身份未变、generation 仍是当前桶代次。满足条件才写入，旧结果记 `superseded`。
- 日账单更新、桶状态更新与任务项完成在一个事务内提交；父任务计数从子项重算或事务更新，防止崩溃后进度虚增。
- `onboard.go` 的初次账单写入也复用校验和 generation 写入服务，不能继续独立写旧式时间戳代次。
- 日账单请求是读取操作；服务重启后过期租约项可安全重试。上传任务原有“结果未知不自动重放”规则不变。

### 6.3 重试与错误

- 超时、连接失败、HTTP 408/429/5xx 可重试，建议最多三次总尝试；指数退避加随机抖动，429 优先采用有效 `Retry-After`。
- 401/403 归为连接授权问题，停止同连接的本次后续请求并给未执行项标明确原因；不映射成 Claude 账号被封禁。
- 日期/参数拒绝、响应 schema 错误、range 不匹配、身份映射改变不自动重复请求。
- 准备进入执行队列或重试时重新验证 90 天下界；跨业务日后失效的项标为 `WINDOW_EXPIRED`。
- 错误明细包含连接、账号本地 ID、供应商账号 ID、日期、错误码和可重试性；不记录 Token、密码、凭证或原始敏感响应。

### 6.4 调度

- metrics 保留每两分钟采集。
- 账单改为每两小时采集今天及前两天；每天低优先级重查今天及前六天。
- 手动补采优先于大范围历史扫描，自动任务与手动任务共用队列、去重和并发保护。
- 初次接入显示缺失覆盖情况，由用户主动选择历史范围；不在每次打开页面时触发大规模上游查询。
- 调度依据平台连接时区；连接时区改变后已有账单保存原时区，新同步使用新时区，页面提示历史口径变化。

## 7. 页面修改

为“平台离线账单”建立独立组件和 API 模块，避免继续在 `App.vue` 的通用列表中堆积远端同步状态。

建议拆为 `web/src/components/PlatformBills.vue`、`BillSyncDialog.vue`、`BillSyncProgress.vue` 和 `web/src/bills-api.ts`，共享现有布局和样式。普通账号/代理列表维持现有行为。

### 7.1 查询区

- 平台连接必选；只有一个连接时默认选中，多个连接时由用户选择。
- 账号支持多选，显示邮箱/名称、供应商账号 ID；日期支持自定义、今天、近 7 天、近 30 天、近 90 天。
- 关键词支持账号、别名和两类上游 ID；日期、关键词、页码、页大小传给服务端。
- 点击“查询”只查本地，显示“已保存数据”；点击分页或切换页大小重新请求服务端，不对截取列表做伪分页。
- 快速切换条件时使用请求序号或 AbortController，禁止旧响应覆盖新条件结果。

### 7.2 表格与合计

- 显示账号、供应商账号 ID（上号返回 id）、平台账号 ID（aid，可空）、业务日期、请求数、四类 Token、平台消费、revision、采集时间和验证状态。
- 金额与大计数使用字符串安全格式化；金额由整数分拆分，不经过不精确的 Number 求和。
- 区间合计来自服务端全匹配结果；展示覆盖缺失和历史未复核提示，有缺项时标注“部分数据合计”。
- 当平台没有返回该账号日的数据时显示“无返回”；网络失败显示“同步失败，展示历史值”；显式零值才显示 0。

### 7.3 补采与进度

- 按钮命名为“同步账单”，打开账号与日期选择；区分已选账号和当前连接全部关联账号。
- 日期使用平台时区边界校验，服务端再次校验。
- 任务创建成功只提示“已加入同步队列”，随后每 3 秒轮询；离开页面停止轮询，任务继续在服务端执行。
- 进度展示已处理/总账号日数及更新、未变化、无返回、失败数量。结束后刷新当前查询条件。
- 全部成功：提示本次实际更新与无返回数量；部分失败：黄色提示并可展开失败明细；全部失败：红色错误。不能只凭 HTTP 202 显示全部成功。
- 支持重新打开最近任务和重试失败项；选择超出可查窗口的历史时仅允许本地查询，给出不能补采的日期说明。
- 用户需要看到账号数、日期与状态，不在主流程展示 generation、锁、SQL 分片等实现细节。

## 9. 验收用例

### 9.1 客户端与日期

- 上游数值和字符串金额转换准确，保留已修复的所有字段、大计数与显式零值回归。
- 请求 1、100、101 个 ID；前两种合法，101 个必须先由业务分批或被客户端拒绝。
- 两种日期输入格式、无效日期、闰日、起止反转、未来结束日期、90 天下界及前一天。
- 上海业务时区与机器 UTC/其他时区结果一致；采用含夏令时的测试时区验证不能用 24 小时代替日历日。
- 完整 `range`、数字/字符串日期、缺失/非法/扩大/裁剪窗口。
- 返回顺序颠倒、账号缺失、额外 ID、重复 ID、null/缺字段、非法计数和 HTTP 错误。

### 9.2 数据与 worker

- 250 账号 × 3 天生成 9 个 HTTP 分片、750 个账号日，映射不串号。
- 重复同步不重复累加；内容不变 revision 不变，内容变化仅增加一次。
- 有效空列表不写伪零；失败不清空已有数据；窗口不匹配不能污染账单日期。
- 故意延迟旧响应，确认不能覆盖新 generation；onboard 与手动/定时同步共用保护。
- 超时、429、5xx 能按策略重试；401/403 停止对应连接；重启后恢复过期租约且不重放上传。
- 幂等同请求复用、同键异请求 409、结束后新的主动修订允许执行。
- 迁移旧表后，历史值和旧 revision 保留、验证状态为待复核，旧 sync_generation 不影响新写入。
- 所有成功、部分失败、全部失败、无返回、过期项和身份变更都能在任务中查到。

### 9.3 查询和页面

- 生成超过 1000 行，较早日期仍可筛到；跨页总数与合计正确。
- 账号、连接、日期、关键词、revision 和归档筛选在服务端生效；稳定排序不重复漏页。
- 新接口 ID 语义与旧兼容字段明确，aid 缺失不伪造。
- 超过 JavaScript 安全整数的 ID/计数及金额展示准确；当前页与全结果合计明确。
- 202 只显示排队，partial 显示部分失败，重试仅包含失败项；无返回不显示为零消费。
- 页面查询不产生上游请求；只有显式同步或定时任务产生请求。

实施时执行 `go test ./...`、对并发同步路径执行有针对性的 `go test -race`、`go vet ./...` 和 `web` 的 `npm run build`。新增测试验证日期、响应和状态行为，不只验证组件是否渲染。

真实联调仅查询已有授权账号：核对同一账号日的供应商账号 id、平台 aid、请求数、各类 Token、金额和实际窗口；不为验收新建或重复上传账号。没有有效 OpenAPI 配置时，只报告本地模拟验证通过，不能报告真实联调完成。

## 10. 发布、历史修复与恢复

1. 保留当前源码与可运行二进制、文件 SHA256、当前配置位置；加密密钥持续复用，不为修复重新生成。
2. 使用 SQLite backup API 备份实际运行的数据库并校验可打开；保留 schema 版本和日账单行数/金额摘要。
3. 在数据库副本执行迁移与回归验证，确认旧行数量、金额和账号关联不变。
4. 部署新接口与 worker，再切换前端、重启服务，验证登录、查询、分页、排队和失败反馈。
5. 对未复核历史优先补查最近三天，再按用户选择补查允许窗口内的日期；不根据既存零值直接修改计数。
6. 若应用需要回退且数据库未损坏，先停止 worker，使用兼容旧列的旧版本保留已采集的新行；若迁移或数据发生错误，保留失败库后恢复一致性备份，同时说明备份之后的新数据需要重新采集。禁止恢复主库时遗留不匹配的旧 WAL/SHM。
7. 恢复验证在额外数据库副本进行；保留最终修改版和新采集记录供检查。

交付物应包含代码差异、迁移文件、测试输出、前端构建产物、本地启动验证、真实联调是否完成的说明及备份/恢复记录。

## 11. 开发前固定的默认选择

本方案推荐：单连接查询、默认近 30 天、日粒度缓存、服务端分页、显式异步补采、每批最多 100 账号、默认 10000 账号日任务上限、同连接单请求并发、HTTP 总尝试最多三次。以上资源与调度值可通过配置调整。

需要供应商联调确认的仅包括：90 天边界的实际口径、`range` 是否始终返回及其类型、空列表的业务含义、真实限流和失败状态。确认前采用本文的日期解释、严格窗口校验、无返回不等于零、保守调度策略，不自行杜撰额外上游参数。
